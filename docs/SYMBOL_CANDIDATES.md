# 記号の追加候補（Issue #58）

## 使い方

通常の変換後、もう一度Ctrl＋Jを押して追加候補を取得する。
APIから追加候補を正常に取得した後だけ、入力全体に一致する記号をローカルで補う。
LLMがひらがな候補を返さなくても検索できる。

| 元の入力 | 補う記号の例 |
| --- | --- |
| hoshi／hosi／ほし | ☆・★ |
| kuroboshi | ★ |
| maru1／maruichi／まる1 | ① |
| maru2 | ② |
| yajirushi | →・←・↑・↓ |
| mugendai | ∞ |
| ten／nakaguro／. | ・（Sumibi独自の優先候補） |

ASCIIの大文字小文字は区別しない。文章中の一部、前後に空白がある入力などは一致としない。
ピリオドの一括置換は行わない。①などを別文字へ変える互換正規化は行わない。

## 既存処理との関係

- 初回変換、自動変換の判定・トリガー、APIへの送信内容は変更しない。
- LLM候補の順序と本文を変えず、中黒→Mozc記号→既存Sudachi候補の順に重複を除いて補う。
  辞書からの新規追加は合計最大10件。現在の候補・原文は既存の入力セッションが保持する。
- 追加した候補だけを既存の「辞書」表示の対象にする。LLMが返した同じ記号はLLM由来のまま。
  ラベル・注釈・字形指定を入力本文へ挿入しない。
- 索引や検索結果をAIへ送信せず、記号検索のための追加通信も行わない。
  追加候補取得のAPIエラー時にはローカル記号だけの代替処理を行わない。
- Mozc索引が欠損・読取不能でもLLM、既存Sudachi、中黒の処理は独立して使える。
- 範囲照合、候補選択、Esc、Undoの書込順序は既存の仕組みを変更しない。
  Codexの長文読取制約や、調査中の自動変換の見送りを解消する変更ではない。

出典・固定ハッシュ・加工内容・再生成手順は[ThirdParty/Mozc](../ThirdParty/Mozc/README.md)に記録する。
ライセンスはアプリ内の設定画面から確認できる。一般的なライセンスUIの全面刷新は含めない。

## 検証と実機確認

模擬通信・模擬Keychain・専用UserDefaultsで候補取得を検証する。実APIへのテスト送信は行わない。
かな・別名・数字・大文字小文字、完全一致、互換文字の保持、中黒優先、候補上限、重複と出所、
欠損時の動作、APIエラー時の非補完、要求本文の非変更と通信回数、現在候補・原文の保持を確認する。
生成処理の単体テストと、固定元データから再生成した索引のバイト一致を別途確認する。
配布物検査では記号索引とMozcライセンス2ファイルの同梱を必須にする。
