# Sumibi-winへの引き継ぎ仕様

確認日: **2026-10-20**／関連: [Issue #63](https://github.com/kiyoka/Sumibi-mac/issues/63)。
これはMac版の動作と実装から引き継ぐ情報であり、Windows版の方式・API・対応OSを決定する文書ではない。
Windows用リポジトリの作成、コード移植、配布や署名は本作業で行っていない。

## 1. 最初に読むものと基準

1. 本書で共通の操作・非同期処理・安全条件を把握する。
2. [実装照合記録](IMPLEMENTATION_AUDIT.md)でmain／PR／未コミット作業版を区別する。
3. [SPEC](SPEC.md)で合意要件を読み、未実装の要件を現在の機能として取り込まない。
4. [技術解説](TECHNICAL_OVERVIEW.md)、[Tests/README](../Tests/README.md)からコードと回帰ケースを参照する。

基準mainは`d2b96fc`（PR #65まで）。記号サポートもPR #61でmain統合済み。
原文比較と診断画面は#62対応ブランチに実装。現在の実機アプリがmainと同じ内容とは限らない。
将来参照するときはPRの統合状態を再確認し、対象コミットを固定する。
APIキー・ユーザー設定・入力履歴・署名秘密鍵を引き継ぎ資料へコピーしない。

## 2. 共通の製品動作

- ローマ字／英語を通常どおり入力し、追跡中の範囲を控えめな下線で示す。
- 手動変換の初回は1候補を取得し、原文を結果へ置換して確定する。最初から候補一覧を開かない。
- 同じ対象で再度変換すると、元の原文＋現在結果で追加候補を要求する。現在の日本語だけを新しい原文にしない。
- 追加取得は現在結果を維持し、別候補を選んだときだけ対象範囲を書き換える。
- 現行要求は現在結果を含む最大12候補。要件の「第二候補以降10件」との差は未決で、辞書追加10件とは別。
- Enterは変換指示ではない。通常入力では原文を確定して追跡を終え、元のEnterをホストへ渡す。
- 修飾なしEscは、候補窓があれば窓を閉じる。追跡中なら原文を残して下線を解除し、応答待ちなら取り消す。
  対象がないEscはホストへ渡す。取消後の遅延応答は非適用。修飾付きEscは別操作。
- 選択範囲の変換も可能。ただし古い追跡や再変換と競合させず、選択した全文を読み取れる場合だけ行う。
- ホストの標準Undoを守る。Macでは原文確定→結果の範囲置換で1回のUndoを目標にしているが、
  Windowsで同じ書込順序を使うべきか、編集履歴が同じ単位になるかは別途検証する。

Macの変換キーはCtrl＋J／右Command短押し／かな。Windowsのキー割当は未決で、Commandを機械的に
別キーへ置換する仕様ではない。[InputSession](../Sources/SumibiCore/InputSession.swift)は意味上の入力イベントと
効果を表す純粋な状態機械として参照できる。OSキーコードや実際の入力先への書込はアダプターの仕事。

## 3. 手動変換と自動変換を混同しない

| 観点 | 手動変換 | Decisions自動変換 |
| --- | --- | --- |
| 開始 | 明示的な変換キー | 独立した同意＋有効化後、日本語らしさが閾値以上 |
| 待機中の入力 | キーを順番に蓄積し、対象確認後に処理 | キーを即時処理。古い判定・変換結果は捨てる |
| 新しい文字 | 旧結果の後ろへ反映するために待機 | 原文・世代が変わるので旧結果を適用しない |
| 移動・切替・Esc | 取消と文字救済。制御キーを別入力先へ流さない | 待機・観測を取消。未確定原文は移動前に保持する |
| 通信と反映待機 | API要求と反映先の探索は別 | 判定→変換→原文／結果の読取確認を直列管理 |

現行Macでは、手動待機中に蓄積されたEnter等が「後でホストへ渡す」効果になっても、
`deferredControls`に記録するだけで再送しない。待機中のEnterが後でチャット送信されるとは約束しない。
Windows側はこの差を明示的に設計・テストし、遅延キーや疑似キーを無断で実行する仕様を作らない。
手動待機キーと救済文字の容量・期限は未実装の課題で、Decisionsの待機256状態とは異なる。

## 4. 決して省略しない入力保護

- 要求ID、入力世代、対象入力先、選択・範囲、保持原文、設定・同意を確認してから結果を適用する。
  キャンセルだけに頼らず、キャンセルに間に合わなかった結果も検査して捨てる。
- 対象が読取不能・不一致なら結果を書き込まない。末尾の部分一致、近傍の全文検索、別欄への救済文字の自動挿入で代替しない。
- 同じ原文が前方にも存在する例、カーソル遅延、確定前後で座標が変わる例をテストする。
- 範囲の座標系と文字数を区別する。Macの送信上限はSwift `String.count`（書記素クラスタ）、
  置換範囲はUTF-16。絵文字や結合文字を含むテストが必要で、UTF-16長やコードポイント数をそのまま文字数にしない。
- 原文照合の現行実装はSwiftの文字列比較であり、UTF-8バイト比較と同義とは限らない。
  大小文字・空白・互換正規化で照合条件を緩めない。移植先のUnicode比較方式を明示してテストする。
- 自動変換の対象・セキュア入力・入力活動・前面アプリの検査はOSアダプターにある。
  Windowsでパスワード等の保護と検出をどう保証するかは別途調査する。
- Mac固有の「相対末尾カーソル」の限定的な許容や0.3秒のコントローラー再生成対策を、Windowsの仕様へ無条件に移さない。

参照: [TextReplacementTracker](../Sources/SumibiIME/TextReplacementTracker.swift)、
[AmbientInputSnapshot](../Sources/SumibiIME/Conversion/AmbientInputSnapshot.swift)、
[AmbientResultApplier](../Sources/SumibiIME/Conversion/AmbientResultApplier.swift)。
これらのテストにある異常入力先の例を、Windows実装用の受入ケースとして利用する。

## 5. 変換APIと上限（Mac実装の契約）

通常変換は[OpenAICompatibleClient](../Sources/SumibiCore/OpenAICompatibleClient.swift)の
Chat Completions互換形式。設定済みURLが完全な`chat/completions`でなければ`v1/chat/completions`を補完する。
要求はBearer認証、`model`とsystem/userの`messages`。既定接続先は`https://api.openai.com`、
既定モデルはコード上`gpt-6-sol`。代表モデルには[ModelPreset](../Sources/SumibiCore/ModelPreset.swift)の
指定を付けるが、自由入力モデルへ同じオプションを無条件に送らない。
これはMacが現在使う値の記録であり、すべての互換サーバーへの対応保証やモデル移行の指定ではない。

- 初回1候補、追加最大12候補。応答本文のJSONオブジェクト／配列、部分的なJSON、最後に通常文字列を解析し、
  空・重複を除いて上限へ収める。厳格なJSON Schema保証を使う実装ではない。
- 可変部分は原文＋現在結果＋ユーザー辞書の合計1,000文字。固定プロンプト・JSONは計数外。
  ユーザー辞書全体を漢字変換へ送る。周辺文脈欄は空、追加文体指示は未実装。
- 変換タイムアウト既定60秒。401/403、429、5xx、その他HTTP、タイムアウト、オフラインを分類する。
  UIへ生の通信エラーや応答本文を出さず、固定の原因と対処を使う。
- 変換APIの現行クライアントは共有URLSessionを使い、Decisions専用の転送拒否・一時セッションと同一ではない。
  Windowsで接続先・リダイレクト・キーの扱いを実装するときは別途安全性を検討する。

プロンプトと候補解析の正確な文面は[Conversion.swift](../Sources/SumibiCore/Conversion.swift)にある。
同音異義語・タイプミス補正・かな／カナ／漢字・送り仮名・英訳は追加候補の指示であり、モデルの出力保証ではない。

## 6. Decisionsの契約と費用保護

固定の`POST https://api.openai.com/v1/decisions`、モデル`gpt-6-luna`、predicate質問を使う。
公式の型付き質問と名前付き回答は[OpenAI公式仕様](https://developers.openai.com/api/docs/guides/decisions#how-decisions-work)を
2026-10-20に確認した。以下の集約・制限はSumibi独自の設定で、API全体の上限ではない。

- 初期値: オフ、同意なし、閾値0.5、10秒、1状態512文字、通信上限10,000回。
- 現行Macは自身が保持する単一行のローマ字系入力だけを対象にする。許可文字は
  [AmbientText](../Sources/SumibiCore/Decisions.swift)を参照。英語を確実に除外する決定的な判定ではない。
- 200ms固定窓は後のキーで延長しない。UIタイマーが遅れてもキー時点で期限を確認し、最大32状態ごとに分割する。
  未送信観測は256件まで。各状態をIDで質問へ対応付ける。最新の対象に対応する回答だけを使う。
- `answers`は件数・名前集合・重複・型・有限の0～1確率を検証する。並び順だけで対応させない。
  拒否応答を区別し、古い入力の拒否が現在の有効な判定を妨げないようにする。
- 判定・変換・確認は同時1件。失敗・取消も送信直前の予約時に通信1回として数える。
  これは集約した状態数や厳密な請求額ではない。再起動・アプリ切替で回数をリセットせず、明示リセットのみ。
- 既存の変換キーを使うのは公式HTTPSホスト設定のときだけ。カスタムサーバー用キーは判定へ送らない。
  変換への同意と自動送信への同意を分離し、同意取消で自動変換をオフにする。
- 周辺文脈・辞書・クリップボード・アプリ名・キー操作を判定へ送らず、未確定本文だけを使う。
  専用の一時セッション、Cookie・共有資格情報・URLキャッシュなし、HTTP転送拒否。自動再送なし。
- 原文確定後の読取確認には単調時計の0.5秒期限を設ける。置換後の結果確認は100ms間隔・最大5回で約0.5秒が目安だが、
  現行の結果確認ループには同じ単調時計の期限検査がなく、スケジューラー遅延による延長を実時間上限で保証しない。
  新しい入力は即時処理して古い試行を取消す。
  Macの反映遅延対策をWindowsにも必要と決め付けず、同じ安全条件を別方式で満たせるか検証する。
- 旧Jevから有効な閾値・上限だけを移行し、旧キー・同意・有効化・回数は転用／削除しない。
  Windowsの新規導入でこの旧Mac設定移行を実装する必要があるかは未決。

参照: [DecisionsClient](../Sources/SumibiCore/DecisionsClient.swift)、
[DecisionsCoordinator](../Sources/SumibiIME/Conversion/DecisionsCoordinator.swift)、[詳細と実機履歴](DECISIONS_CONVERSION.md)。

## 7. 辞書・設定・診断

- ユーザー辞書は`よみ = 変換後`、100件・保存文字列2,000文字まで。ただし送信合計1,000文字は別判定で、
  保存できた辞書でも変換要求が超過する場合がある。読みは小文字ASCIIの印字可能文字、空白・重複を拒否。
- SudachiはLLMに全ひらがな単語の候補がある場合の読み検索。記号（PR #61で統合済み）は元入力全体から独立検索。
  中黒→Mozc→Sudachiで合計10件、LLM順序・現在候補・出所を維持し、本文へ注釈を混ぜない。
  索引はローカル専用で、検索のためのAPI追加要求やAPI失敗時のオフライン代替は行わない。
- Mozcの固定元データ・生成処理・ハッシュ・LICENSEは[ThirdParty/Mozc](../ThirdParty/Mozc/README.md)、
  Sudachiは[ThirdParty/SudachiDict](../ThirdParty/SudachiDict/README.md)を参照する。
  データをWindowsへ同梱する場合も出典・ライセンスを落とさず、フォントや字形画像をコピーしない。
- 接続先・モデル・辞書は明示保存。Decisions閾値・上限等は自動保存。秘密キーは設定本文と分離したOSの安全な保存先を使う。
  MacのKeychainサービス名やUserDefaultsドメインを、そのままWindowsの保存契約にしない。
- エラー通知は処理状態から分離し、明示解除まで最新1件を保持する。エラー解除を次の変換の前提にしない。
  緑の判定印は結果適用の成功印ではなく、直近の判定と現在入力の状態が異なる場合もある。
- 本文のログ保存は行わない。診断イベントは固定分類と数値だけ。一時デバッグ（#62作業版）は
  独立画面で明示オン・メモリ内限定・再起動後オフ。[扱い](DIAGNOSTICS_SETTINGS.md)を維持する。

## 8. Windowsで改めて決めること

| Mac固有の参照実装 | 引き継ぐ目的／Windowsで未決の点 |
| --- | --- |
| InputMethodKit・入力ソース登録・単一アプリ | 入力範囲と寿命の安全な管理。WindowsのIME方式・対応OS・プロセス分割は要調査 |
| 0.3秒の再生成判定・client poke | 応答先の寿命を守るための観測依存の対処。数値・擬似編集を直接移さない |
| AppKit候補窓・NSStatusItem・カーソル横の印 | 非フォーカス奪取・候補選択・エラー確認。WindowsのUIと座標取得を別途設計 |
| Command／かな・ターミナルのキー配信 | 明示変換・取消・ホスト操作を区別。Windows側キー割当・TUI対応を検証 |
| Keychain・UserDefaults・SMAppService | 秘密保存・設定・起動制御。Windowsの保存方式と導入権限は未決 |
| Developer ID・Apple公証・home限定pkg | Mac専用の配布経路。Windowsの署名・インストーラー・削除・更新は別設計 |
| EmacsのBundle ID除外 | Emacs版との競合回避という意図だけ参照。Windowsの対象識別と除外一覧は未決 |

既知のCodex長文制約、短文の内容不一致、失敗後の停止、#28は[照合記録](IMPLEMENTATION_AUDIT.md)を参照。
Macで発生したことをWindowsで再現する仕様にはせず、検証ケースとして扱う。

## 9. 最小限の受入テストと保守

- 純粋状態機械：初回・追加・選択、成功／失敗、連打、空文字、待機キー順序、Escと遅延応答。
- 非同期競合：新しい文字、削除、カーソル移動、別欄・別アプリ、手動と自動の競合、同意・接続先変更。
- 偽入力先：読取不能、同じ長さで別内容、部分文字列、同じ原文の前方重複、古い選択位置、UTF-16と書記素数の差。
- 費用・認可：未同意／キー欠損／異なる接続先では送信しない。固定窓・分割・回数上限・取消・拒否／不正回答を模擬する。
- 候補：重複・上限・現在候補と原文・出所、辞書欠損、記号の①等の保持、API要求が増えないこと。
- プライバシー：テストは専用設定・偽キー・模擬通信だけ。本物のキーや入力原文をログ・検証資料へ残さない。
- 実機：実際の対象アプリで1回のUndo、Enter／Escのホストへの到達、遅延結果の非適用と再開を確認する。
  通常の入力欄だけでなくTUI・複数ウィンドウ・セキュア入力・導入／更新／削除を分ける。

Macの330件という過去の成功数はWindowsのテスト結果ではない。共通ケースを移植先で再実行し、
OS・アプリ・版・自動／実機の区別を付ける。[資料の更新手順](README.md)に従って変更履歴を追う。
