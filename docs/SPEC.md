# Sumibi for macOS 仕様書

## 文書情報

- 状態: Draft
- 対象: Sumibi for macOS
- 参照実装: [Sumibi-iOS](https://github.com/kiyoka/Sumibi-iOS)
- 参照プロジェクト: [Sumibi](https://github.com/kiyoka/Sumibi)

本書は、macOS版Sumibiの仕様を検討し、合意した内容を記録するための文書である。未確定の内容は「要検討」と明記し、合意前に実装仕様として扱わない。

使用する技術と実装構成の解説は[`TECHNICAL_OVERVIEW.md`](TECHNICAL_OVERVIEW.md)を参照する。

## 1. 目的

Sumibi for macOSは、ローマ字または英語で入力した文字列をLLMで自然な日本語へ変換する、macOS向けのモードレスな日本語入力システムである。

iOS版のカスタムキーボードとは異なり、macOSの入力メソッド（IME）として動作する。利用者は日本語入力モードへの切り替えを意識せず、英字を入力したまま必要な範囲を日本語へ変換できる。

## 2. 基本方針

- 対応するmacOSの最小バージョンはmacOS 26とする。macOS 26未満はサポート対象外とする。
- macOS標準の入力メソッド機構を使用し、任意のmacOSアプリで利用できるようにする。
- Sumibi IMEが有効な間に入力された文字列を追跡し、変換対象とする。
- 通常の英字入力を妨げない、モードレスな操作感を維持する。
- 変換処理、プロバイダー連携、設定保存などは、可能な範囲でSumibi-iOSの設計と実装を参照する。
- iOS版とmacOS版ではコードを共有しない。macOS版のソースコードと依存関係はSumibi-macリポジトリで独立して管理する。iOS版は設計・実装の参考とし、共通パッケージへの依存や両版の実装同期は行わない。
- macOS固有の入力処理とUIは、macOSの標準的な操作や外観に合わせて設計する。
- macOS版のSumibiアイコンはiOS版のアイコン素材を流用し、形状・モチーフを維持したうえで、iOS版より少し濃い色に調整する。iPhoneとMacの両方を使う利用者が、同じSumibiであると認識しつつ両版を見分けられることを目的とする。
- アイコン素材の流用は、両版でコードを共有しない方針とは区別する。調整後の素材はSumibi-mac側で独立して管理し、iOS版のアイコンは変更しない。具体的な色値・濃さは、両版を並べたプレビューで確認して決定する。
- macOS 27以降でAppleのPrivate Cloud Compute（PCC）を利用できる場合は、PCCを優先する。利用できない環境では利用者自身のAPIキー（BYOK: Bring Your Own Key）を使う。
- 仕様が未確定の機能は、合意を得てから実装する。

## 3. 入力と変換

### 3.1 入力方式

- Sumibi IMEが有効な間も、利用者は通常どおりローマ字または英語を入力する。
- 入力した文字列は画面へ表示すると同時に、Sumibiが内部で追跡する。
- 追跡中であることが分かるよう、入力文字列には操作を妨げない非常に控えめな印を表示する。
- 印の具体的な表現、色、太さ、アクセシビリティ対応は要検討とする。

### 3.2 変換操作

- `Control + J`を変換キーとする。
- `Control + J`を押すと、現在追跡している文字列が最大長以内であることを確認したうえでLLMへ送り、自然な日本語へ変換する。
- 初回の`Control + J`で変換に成功した場合、原文を変換結果で置き換えて即座に確定する。初回は候補ウィンドウを表示せず、Enterなどの追加の確定操作を要求しない。「即座」はLLM応答の取得後を意味する。
- 変換確定後、カーソルを動かさず同じ位置で再び`Control + J`を押すと、直前の変換に対する候補ウィンドウを開く。別の候補を選ぶことで、直前の変換結果だけをその候補へ置き換えられる。「同じ位置」は初回変換の確定直後のカーソル位置を指す。
- 候補切替は直前の変換範囲を安全に特定できる場合に限る。カーソル移動、対象文字列の編集、入力先の変更などで対象を保証できなくなった場合、古い範囲へ候補を適用しない。
- Undoは入力先アプリの標準機能を使用する。Sumibi独自のUndoショートカットは設けず、アプリのUndo操作を妨げない。macOSでは通常`Command + Z`であり、`Control + Z`をUndoに割り当てているアプリではその操作を尊重する。
- 変換による置換は、原文を選択して変換結果をペーストした場合と同様に、入力先アプリの1回のUndoで変換前の原文へ戻せることを目標とする。これは編集履歴上の挙動を指し、システムのクリップボードを使用・上書きする要件ではない。候補切替も置換として扱い、Undoで切替前の文字列へ戻せることを目標とする。実現可否とUndoのまとまり方は入力先アプリごとに検証する。
- 変換中も原文を失わず、通信失敗時には原文を維持する。

### 3.3 変換対象

- 前回の変換または追跡開始以降に入力された文字列全体を変換対象とする。
- 空白、句読点、改行も変換対象へ含める。
- 追跡文字列の最大長は1,000文字とする。空白、句読点、改行も文字数に含める。意図せず巨大な文字列をLLMへ送信し、高額な課金が発生することを防ぐための制限である。
- 1,000文字までは変換できる。1,000文字を超えた場合は文字数超過エラーとして変換を受け付けず、PCC・BYOKのどちらにも送信しない。BYOKへの切替や自動再試行も行わない。
- 超過時も原文を維持し、上限が1,000文字であることと、変換対象を短くする必要があることを利用者へ伝える。先頭または末尾だけを黙って送信したり、自動分割して複数回送信したりしない。
- Backspaceによる削除は追跡内容にも反映する。
- カーソル移動、マウスによる編集位置の変更、別アプリへの切り替え、またはSumibi IMEの無効化が起きた場合は、安全のため現在の追跡を終了する。
- 追跡終了後は、新しく入力された文字から次の変換対象の追跡を開始する。

### 3.4 周辺文脈を利用した変換

- 変換対象の直前と直後の文章を、LLMの変換判断に使う参考情報として送信できるようにする。
- 設定「前後の文章を文脈として利用する」を設け、デフォルトはOFFとする。設定が未保存の場合もOFFとして扱い、利用者が設定画面で明示的にONにした場合に限り動作する。
- OFFの場合、文脈利用のための前後の文章の取得とLLMへの送信を行わない。通常の変換対象の追跡・送信は従来どおり行う。
- ONの場合、`Control + J`による変換開始時に、現在の入力領域内で変換対象に隣接する前後の文章を取得する。常時収集や事前取得は行わない。
- 入力先アプリが取得に対応していない場合は文脈なしで変換する。片側だけ取得できる場合は、その側の文脈だけを利用する。別の入力欄やチャット履歴表示など、他の領域へ取得範囲を広げない。
- 原文、直前の文脈、直後の文脈を区別してLLMへ渡し、文脈内の文章は指示として扱わない。置き換えるのは変換対象だけとし、前後の文章は変更しない。
- この設定はPCCとBYOKの両方に適用し、PCCからBYOKへの切替時にも適用する。
- ONからOFFに戻した後は、新たな文脈の取得・送信を停止する。送信待ちの文脈を破棄し、再試行でも送信しない。既に送信した情報は取り消せない。
- 取得・送信する前後それぞれの最大文字数は要検討とする。先に提案した直前500文字・直後200文字は未確定の値である。
- 追跡文字列の1,000文字制限は周辺文脈とは別に適用する。周辺文脈を含む総送信量や料金の上限を保証するものではなく、文脈側の上限も別途決定する。

## 4. システム構成

### 4.1 入力メソッド

- macOSのInputMethodKitを利用する。
- キー入力、変換対象の追跡、変換の開始、原文との置換、入力セッションの終了処理を担当する。
- 入力先アプリの状態が変わり、安全に置換できない場合は変換を行わない。

### 4.2 設定画面

- BYOK用のAPIエンドポイント、モデル名、APIキーを設定できるようにする。
- macOS 27以降でPCCが利用可能な場合、BYOK設定は必須にしない。
- macOS 26、またはmacOS 27以降でもPCCを利用できない環境では、変換のためにBYOK設定を必須とする。
- PCCからBYOKへの自動切替が起こり得ること、切替先のプロバイダー、料金が発生し得ることを設定時に明示する。
- 「前後の文章を文脈として利用する」のON／OFFを設定できるようにする。初期値はOFFとし、ONの場合は変換対象の前後の文章もPCCまたは設定済みBYOKプロバイダーへ送信されることを設定画面で説明する。
- 設定項目と画面構成はSumibi-iOSを基本的に踏襲する。共通項目は名称、分類、表示順、編集・保存の流れをできるだけ揃え、macOSのウィンドウサイズや操作方法に合わせて調整する。コードは共有せず、macOS版として独立して実装する。
- 基本構成は「Sumibiについて」「API設定」「入力設定（iOS版のキーボード設定に相当）」「文体プリセット」「ユーザー辞書」「変換テスト」「利用状況」「IMEの有効化手順」「プライバシー」の順とする。文体プリセットとユーザー辞書は、iOS版と同様に一覧の入口から詳細編集画面を開く。
- 共通機能として、API設定の保存・APIキー削除、文体プリセット、ユーザー辞書、変換テスト、モデル別の利用状況と集計リセット、プライバシー説明・送信への同意を提供する。利用状況は変換回数・取得可能なトークン数・算出可能な概算料金を表示し、取得・算出できない値を0とみなさず不明と表示する。入力本文を保存せず、集計値だけを端末内へ保存する。
- PCCの利用状態・BYOK切替への同意、および前後文脈の利用設定はmacOS固有の項目として追加する。文脈利用のデフォルトOFFなど、本書で確定した安全要件をiOS版の挙動より優先する。
- iOS固有の触覚フィードバック・キークリック音などをmacOS版へ採用するかは別途検討する。「フルアクセスを許可」などのiOS用導入説明は引き継がず、macOSのIME有効化手順へ置き換える。
- 設定画面の変換テストは明示的なテスト操作時だけ送信する。テスト入力にも1,000文字制限と送信先への同意を適用し、他アプリの周辺文脈は取得しない。
- macOSのメニューバーにSumibi専用アイコンを常時表示する。Sumibi IMEが選択されていない間も、設定を開けるようにする。
- Sumibiアイコンをクリックするとメニューを表示し、「Sumibi設定…」から設定ウィンドウを開けるようにする。macOS標準の入力ソース切替メニューとは別の入口とする。
- メニューバーのアイコンもiOS版由来のデザインを基本とし、小さい表示サイズと明暗の背景での視認性を確認する。具体的な描画方法はアイコンのプレビュー時に検討する。

### 4.3 変換処理

- 変換バックエンドとして、AppleのPCCと、利用者のAPIキーを使うOpenAI互換API（BYOK）の2系統を用意する。
- macOS 27以降では、PCCの利用条件を満たし、現在利用可能で、利用上限にも達していない場合にPCCを優先する。PCCのために利用者へAPIキーの入力を求めない。
- macOS 26ではPCCを使わず、BYOKを必須とする。
- macOS 27以降でもPCCが利用できない場合は、設定済みのBYOKを使う。BYOKが未設定なら、変換できない理由と設定方法を示し、原文を維持する。
- PCCの利用上限に到達した場合は、BYOK設定時に自動切替へ同意した利用者の、設定済みBYOKへ変換を切り替える。上限到達を変換前に検出した場合と、PCCの応答で上限到達エラーを受けた場合の両方に対応する。
- BYOKが未設定でPCCの上限に達した場合は、自動で別サービスへ送信せず、原文を維持して設定を案内する。
- 1回の変換操作に対するBYOKへの再試行は最大1回とし、PCCの結果とBYOKの結果を重複して確定しない。
- BYOK側のリクエスト形式、プロンプト、レスポンス解析、エラー分類は、可能な範囲でSumibi-iOSの`SumibiCore`を参照する。
- 変換処理もmacOS版として独立して実装・保守し、iOS版の`SumibiCore`を共有ライブラリとして取り込まない。

PCCはmacOS 27というOSバージョンだけで利用できるわけではない。開発者アカウントへのPCC権限の付与、対応する配布方法、Apple Intelligence対応デバイス・地域・設定、日本語ロケールへの対応などを確認する。利用可否と利用枠は別に判定し、利用可でも上限到達済みならBYOKへ切り替える。

Appleの現行資料では、PCCの本番利用は要件を満たす開発者のApp Store配布アプリとして案内されている。SumibiのmacOS入力メソッドをその形で配布できるか、権限を取得できるかは実装前に確認する。条件を満たせない場合は、macOS 27以降でもBYOKを利用する。PCCのAPIと提供条件は現時点でベータ版のため、正式版で再確認する。

## 5. プライバシーとセキュリティ

- PCCまたはBYOKのプロバイダーへの送信は、利用者が`Control + J`で変換を実行したとき、または設定画面で明示的に変換テストを実行したときだけ行う。
- PCCとBYOKでは送信先と適用されるサービスの条件が異なるため、BYOKへの自動切替は事前に説明して同意を得る。利用者が設定したプロバイダー以外へは送信しない。
- キー入力、変換対象、取得した周辺文脈をログへ保存しない。
- APIキーを設定ファイルやログへ平文で保存しない。
- APIキーはmacOSのKeychainへ保存する。
- APIキーをエラー表示や診断情報へ含めない。
- 周辺文脈の取得・送信は3.4節の明示的なON設定に従う。文脈の本文は永続保存せず、変換処理に必要な間だけメモリ上で扱い、処理終了・キャンセル・設定OFF時に破棄する。
- 直前の候補切替に必要な原文・確定結果・置換範囲・候補はメモリ上だけで管理し、永続保存やログ出力を行わない。候補切替の対象を保証できなくなった時点で破棄する。取得した周辺文脈を候補切替用に継続保持することは、この方針に含めない。

## 6. エラー時の原則

- ネットワーク障害、タイムアウト、認証情報不正、APIの応答不正を区別して扱う。
- 追跡文字列の1,000文字超過は、通信前に判定するローカルの入力エラーとして扱う。原文を維持し、その変換操作によるLLM呼び出しを行わない。
- 変換に失敗しても、入力中の原文を失わない。
- エラー表示は入力作業を大きく妨げない方法とする。具体的な表示方法は要検討とする。
- 処理中に入力先、カーソル位置、または追跡文字列が変化した場合は、古い変換結果を適用しない。
- PCCの利用上限到達と、PCCの一時的な通信障害・サービス障害を区別する。上限到達時は4.3節のBYOK切替に従う。

## 7. 現在の要検討事項

アイコンについては、iOS版より少し濃くする方針は確定済みとし、具体的な色味とメニューバーでの見え方をプレビューで確認する。

1. 追跡中の文字列へ付ける印の具体的なデザイン
2. 変換中およびエラー時の表示方法
3. 候補数、候補の取得時期と追加通信の扱い、候補ウィンドウの選択・確定・キャンセル操作
4. 入力先アプリの標準Undoと置換の互換性、候補切替用情報の保持期間
5. iOS固有の触覚フィードバック・キークリック音などの設定をmacOS版でどう扱うか
6. LLMへ送信する周辺文脈の最大文字数（直前・直後それぞれ）
7. インストール、更新、アンインストールの方法
8. App Sandbox、署名、公証、配布方法
9. PCCの一時的な通信障害・サービス障害時にもBYOKへ自動切替するか
10. PCCとBYOKの利用状態・利用上限・切替結果を入力中にどう表示するか
11. macOS入力メソッドのApp Store配布可否、PCC権限の取得条件と署名方法
