# OpenAI Decisionsによる自動変換

## 状態と参照

2026-10-08、利用者の依頼でJev方式を廃止し、Decisionsへ置き換えた。
参照実装は[Emacs版 PR #194](https://github.com/kiyoka/Sumibi/pull/194)、
コミット`dada5cc939c03a2e811949ddcb2effa7c998ed81`。
[OpenAI公式仕様](https://developers.openai.com/api/docs/guides/decisions)の
`POST /v1/decisions`、`gpt-6-luna`、predicate質問、名前付き`answers`を照合した。
自動テストは実APIへ送信せず、実機での自動変換・Undoの確認結果は下記に記録する。
[旧Jevの実機履歴](AMBIENT_CONVERSION.md)をDecisionsの検証済みとは扱わない。

## 判定内容と集約

Emacs版と同じ実験的な「日本語らしさ」の質問文を使う。
日本語のローマ字かどうかを判定し、確率が設定閾値以上なら漢字変換へ進む。
完全な単語・文、スペース・句読点・停止・適切な変換境界を必須にしない。
したがって入力途中でも変換され得る。旧Jevの句読点後500ms待機は廃止する。
判定と漢字変換は別のリクエストで、料金もそれぞれ発生し得る。

- 最初の入力から200msの固定窓。後続の打鍵で延長しない。
- タイマーが遅れても、打鍵時に期限を確認して後続の状態を次の窓へ分ける。
- 適格な各入力状態を間引かず、`state_0`等のID付き本文を共有入力へまとめる。
- 最大32状態ずつ、独立したpredicate質問を同じHTTP要求へ入れる。
  各質問は自身のIDの本文だけを評価し、他の状態を使わないよう指示する。
- `answers`は件数・名前集合・重複・型・有限な0～1の確率を検証し、IDで対応させる。
  回答順序が変わっても、別の本文の評価値を使わない。
- 拒否応答は固定文で扱う。古い状態の拒否は現在の有効な判定を妨げず、
  現在の状態への拒否は変換せずエラー表示する。応答本文は表示・記録しない。
- 判定・漢字変換・書込後の確認を合わせて同時処理は1件。
  通信中も新しい窓を保持するが、古いスコアや変換結果では入力を書き換えない。
- 未送信の観測は256件まで。超えた試行は静かな見送りとして停止・破棄し、
  入力を残して手動変換を案内する。入力そのものを待ち行列へ入れない。

共有入力であるため、質問間の評価干渉が完全にないことやサーバー内部の並列実行、
速度・精度の改善は保証しない。単件との統制された実API比較は実施していない。
設定値`batchWindowMilliseconds = 0`では単件ごとの送信。標準UIは200msの既定値を使う。

## 設定・キー・移行

API設定の「Decisions自動変換の設定…」から設定する。
既定はオフ、モデル`gpt-6-luna`、閾値0.5、タイムアウト10秒、1状態最大512文字、
累積通信回数の上限10,000回。閾値と上限は変更時に自動保存し、
上限の矢印は1,000回単位、下限1,000回。従来の端数値は操作方向へ揃える。
閾値0.5は新規設定・不正設定時の既定値で、保存済みの閾値や旧Jevから引き継ぐ有効な値は変更しない。
2026-10-11、利用者のABCへの切り替え確認後、旧アプリを退避してこの既定値を含む
通常版へ更新・起動し、インストール後の構成・署名検査に成功した。
保存済みの閾値・同意・キーは変更せず、詳細診断ログの有効設定も維持した。

親画面の既存の変換用キーを使用する。別のDecisionsキー項目は作らない。
公式OpenAI HTTPSホスト（標準ポート、認証情報・クエリなし）に設定された場合だけ使い、
カスタムOpenAI互換サーバーや他社のキーをDecisionsへ送信しない。
親画面の変換への送信同意と、この画面の自動送信への独立した同意の両方を必要とする。
親画面でキーを保存・変更する。自動変換画面では短い伏せ字の参照表示だけで、
共有キーの保存・削除操作は設けない。同意取消では自動変換をオフにする。

旧`jevSettings`からは有効な閾値と回数上限だけを移す。旧Jevの有効化・TypeSafeへの
同意・モデル・回数をDecisionsへ転用せず、自動変換オフ・同意なし・回数0で始める。
旧Jevキーを読み取り・コピー・削除しない。旧設定と旧回数も履歴として残す。
新設定は`decisionsSettings`、回数は`decisionsCallCount`に独立して保存する。
以降は再起動・アプリ切替で回数をリセットしない。明示確認付きのリセットのみ。
回数は送信直前の予約数で、集約内の状態数ではなくHTTP要求単位。
失敗・取消も含むため、厳密な請求回数の表示ではない。自動再送はしない。

## 入力保護とプライバシー

既存の入力先・セキュア入力・除外アプリ・候補操作・手動変換中の安全条件を維持する。
macOSではSumibi自身の単一行のローマ字未確定入力だけが対象で、
Emacsと同等の構文解析・日本語文書の収集は行わない。機密入力の前はオフにする。
判定へ送る本文は各状態の未確定入力だけで、操作内容・範囲情報・文脈区分・待機時間・
アプリ名・周辺文脈・辞書・クリップボードは送らない。
固定公式エンドポイント以外へ転送せず、HTTPリダイレクトも拒否する。
Cookie・URLキャッシュ・共有認証ストレージを使わない一時セッションで通信する。

設定・認可・入力先・原文・選択位置・入力活動が変われば古い結果を適用しない。
カーソル移動キーでは、候補選択中を除き、移動をアプリへ渡す前に未確定の原文を
確定し、判定・変換待ちと置換追跡を解除する。原文の確定済み状態では重複挿入しない。
矢印・Home・End・Page Up・Page Downは文字入力として扱わない。
原文確定後の全文照合・追跡付き置換・最大0.5秒の読み取りだけの結果確認は維持する。
確定原文が一時的に読めない場合も、固定した対象の読み取りだけを最大0.5秒再試行する。
その間の入力は待ち行列へ入れず、古い試行を取り消して通常どおり処理する。
原文を再確定せず、全文一致を確認した場合だけ置換する。恒久的な読取制約は解消しない。
原文を読み取れない場合に末尾だけの一致で書き換えず、元の本文を残す。
[Codexの長文エラーの解説](LONG_INPUT_DIAGNOSTICS.md)も維持する。
書き込み順序は従来の原文確定・結果置換のまま。Undoの実機確認結果は下記に記録する。

緑のチェック・赤いエラー印・固定エラーと対処表示を維持し、名称はDecisionsへ変更。
通常ログに本文・キー・生の応答を出さず、固定イベント・分類だけを使う。
Emacs版の打鍵詳細ログは移植しない。一時デバッグの本文表示は従来どおり
既定オフ・明示オン時だけ・メモリ内限定・再起動後オフで、成功・設定変更等で消す。

### 短文の原文確定後の読取失敗への対策（2026-10-13）

利用者の画面で、原文18文字・確定前の範囲(0,18)・確定後の選択(18,0)にもかかわらず、
本文を取得できない失敗を確認した。ログでも22:55:50に適用失敗があった。
位置の数値は整合しており、長文制約だけでは説明できない。入力先の確定反映の遅延は
候補だが、実機での原因確定には至っていない。利用者の許可を得て以下を追加した。

- 原文を従来どおり1回確定した後、読取不能の場合だけ100ms間隔で最大5回、
  単調時計の0.5秒期限内で照合する。UI処理や同期読取が遅れても期限後に置換しない。
- 処理状態は「確定した原文を確認中」。判定・変換・原文確認・結果確認の同時処理は1件。
- 待機中に打鍵・修飾キー操作があれば古い試行を取り消し、新しいキーは通常処理する。
  元の原文は確定済みのまま残る。確定済み原文を手動変換する場合は対象を選択してCtrl＋Jを使える。
- 原文・記録範囲・選択位置・要求ID・入力先・活動・認可・設定を再確認する。
  内容不一致・部分一致では待ち直して上書きせず、中止する。再試行のために新たな検索範囲を広げない。
- 成功時は既存と同じ追跡付き置換を1回だけ行い、必要なら既存の置換後確認へ進む。
  API再送・原文の二重確定・クリップボード・Undo操作は行わない。
- 期限切れでは原文を残して「原文確定後の確認」の失敗を表示する。
  待機状態は必ず解除し、エラー表示を解除しなくても新しい入力は判定できる。
- 詳細ログには`committedSourceWaiting`・`committedSourceRetried`（試行数）・
  `committedSourceConfirmed`だけを追加する。本文・候補・キー・座標は追加記録しない。
