# Sumibi for macOS 技術解説

## 1. この文書の目的

本書は、macOSのIME開発経験がなくてもSumibi for macOSの構成を理解できるように、使用する技術と処理の流れを説明する。

仕様として合意済みの内容は[`SPEC.md`](SPEC.md)を正とする。本書に記載する推奨構成や実装案は、仕様検討と実装設計のための技術的な説明であり、未合意のものを製品仕様として確定するものではない。

## 2. 使用する主な技術

最小対応OSはmacOS 26とする。自己配布版は対応するmacOS 26以降でBYOKを利用する。macOS 26未満はサポート対象外である。

| 技術 | 役割 |
| --- | --- |
| InputMethodKit | macOSの入力メソッド本体と、入力先アプリとの通信 |
| AppKit | 候補ウィンドウ、状態表示、入力メニューなどIME固有のUI |
| SwiftUI | API設定やユーザー辞書などの設定画面 |
| URLSession | 利用者のAPIキーを使うOpenAI互換API（BYOK）との非同期通信 |
| Keychain Services | APIキーの安全な保存 |
| UserDefaults | APIエンドポイント、モデル名など機密ではない設定の保存 |

macOS版では、iOS版のような画面上のキーボードを描画しない。物理キーボードからの入力をmacOS経由で受け取り、入力先アプリへ文字列を返す。

Appleの資料：

- [InputMethodKit](https://developer.apple.com/documentation/inputmethodkit)
- [IMKInputController](https://developer.apple.com/documentation/inputmethodkit/imkinputcontroller)
- [IMKServerInput](https://developer.apple.com/documentation/inputmethodkit/imkserverinput)
- [NSEvent](https://developer.apple.com/documentation/appkit/nsevent)
- [IMKCandidates](https://developer.apple.com/documentation/inputmethodkit/imkcandidates)

## 3. 全体構成

```text
物理キーボード
      │
      ▼
macOS
      │ キーイベント
      ▼
Sumibi InputMethodKit
  ├─ 入力文字列を追跡
  ├─ Control + Jを判定
  ├─ BYOKのLLMへ変換を依頼
  └─ 原文を変換結果で置換
      │
      ▼
メモ、Safari、VS Codeなどの入力先アプリ
```

アプリ内部は、次の3領域に分割する。

以下は論理的な構成図であり、実際のインストーラー内の配置は[自己配布の設計](DIRECT_DISTRIBUTION.md)に従って検証する。IMEと独立した設定アプリ／メニューバー項目が必要になる可能性がある。

```text
Sumibi.app
├─ InputMethodServer
│  ├─ IMKServer
│  ├─ SumibiInputController
│  └─ 候補ウィンドウ
├─ ConversionCore
│  ├─ OpenAI互換APIクライアント
│  ├─ プロンプト生成
│  ├─ レスポンス解析
│  └─ エラー処理
└─ Settings
   ├─ SwiftUI設定画面
   ├─ UserDefaults
   └─ Keychain
```

`ConversionCore`はmacOS版専用の変換処理として実装・保守する。iOS版の`SumibiCore`は設計・実装の参考にするが、コードや共通パッケージを両版で共有せず、実装同期も行わない。macOS版のソースコードと依存関係はSumibi-macリポジトリで独立して管理する。PCCは現行の自己配布版に組み込まない。

## 4. InputMethodKitの役割

InputMethodKitは、macOSの入力メソッドと各アプリの間を接続する標準フレームワークである。

### 4.1 IMKServer

`IMKServer`はSumibiの入力メソッドサービスをmacOSへ公開し、入力先アプリとの接続を管理する。

入力メソッドのアプリが起動すると、`Info.plist`に記載した接続名とBundle IDを使用して`IMKServer`を生成する。

### 4.2 IMKInputController

`IMKInputController`は入力セッションごとに生成される。Sumibiでは、このサブクラスが次の処理を担当する。

- キーイベントの受信
- 入力文字列の追跡
- `Control + J`の検出
- Backspaceやカーソル移動への対応
- 変換処理の開始とキャンセル
- 変換結果の確定
- 入力先変更時の状態破棄

入力先アプリや入力欄が変わるたびにセッションも変わり得るため、追跡状態をアプリ全体の単一変数として管理しない。入力セッションごとに独立して管理する。

### 4.3 IMKTextInput

入力先アプリは`IMKTextInput`を通してSumibiから操作される。

主に次の操作を使用する。

- `setMarkedText`: 追跡中の未確定文字列を表示または更新する
- `insertText`: 変換結果または原文を確定する
- `selectedRange`: 入力先の選択範囲を確認する
- `attributedSubstring`: 置換対象の文字列を確認する

Sumibiが入力先アプリのテキスト領域へ直接アクセスするのではなく、macOSが提供するこの通信経路を使用する。

## 5. キーイベントの処理

入力メソッドは、概念的には次のメソッドでキーイベントを受け取る。

```swift
override func handle(
    _ event: NSEvent!,
    client: Any!
) -> Bool {
    // 押されたキーと修飾キーを調べる
    // 通常文字なら追跡バッファへ追加する
    // Control + Jなら変換を開始する
    // Backspaceなら追跡文字列も削除する
}
```

`NSEvent`から、入力文字、キーコード、ControlやCommandなどの修飾キー、キーリピート状態を取得する。

戻り値の意味は次のとおりである。

- `true`: Sumibiがイベントを処理し、入力先アプリには渡さない
- `false`: Sumibiでは処理せず、入力先アプリへ渡す

基本的な振り分け案：

| 操作 | 処理案 |
| --- | --- |
| 通常の文字入力 | Sumibiが受け取り、追跡文字列を更新する |
| `Control + J`、右Commandのタップ、「かな」キー | Sumibiが受け取り、変換を開始する |
| 通常入力中のEnter | 原文を変更せず確定して追跡を終了し、Enterを入力先アプリへ渡す。変換要求は行わない |
| Backspace | Sumibiが受け取り、追跡文字列の末尾を削除する |
| Commandを使うショートカット | 現在の追跡状態を安全に処理して、入力先アプリへ渡す |
| カーソル移動 | 追跡を終了し、入力先アプリへ渡す |
| IMEの無効化 | 原文を確定し、追跡状態を破棄する |

通常入力中のEnterは、Sumibiが無効な状態で英文を入力する場合と同じ操作になることを仕様とする。未確定文字列の確定だけでイベントを消費せず、アプリ本来の改行・送信などが1回だけ実行されるようにする。Enterを追跡バッファへ追加して保持する処理や、改行の手動挿入とアプリへのイベント引渡しを重複させる処理は行わない。追跡終了後は新しく入力された文字から追跡を再開する。

未確定文字列の確定とEnterの引渡しの組み合わせは試作で検証し、通常のテキスト欄では改行が1回、Enter送信のチャット欄では送信が1回となること、原文が欠落・重複しないことを確認する。Enterで状態が変わった後に届く古い変換結果は適用しない。

候補ウィンドウ内での選択・確定操作、修飾キー付きEnter、貼り付けやその他の特殊キーの詳細な扱いは、別途仕様として決定する。

上記はキーを実際に処理する時点の規則である。リクエスト中は文字とEnter・Backspace・`Control + J`を入力順の待ち行列に入れ、入力先への反映を遅延させる。待ち行列への追加では、送信済み変換対象の更新番号を変更せず、変換をキャンセルしない。

## 6. 追跡文字列と控えめな印

macOSの入力メソッドには「未確定文字列（marked text）」という仕組みがある。Sumibiが`setMarkedText`を呼ぶと、入力先アプリが文字列を表示し、未確定であることを下線などで示す。

未確定文字列を使用する利点：

- 変換対象範囲をmacOSが管理できる
- 原文から変換結果への置換が安全になる
- カーソル移動やアプリ切り替え時に入力を確定できる
- 他のアプリを操作するためのAccessibility権限を必要としない
- 追跡中の文字列へ控えめな印を表示できる

技術上の制約として、未確定文字列の最終的な描画は入力先アプリが担当する。Sumibiから下線の色や太さを指定しても、アプリによっては属性が無視され、macOS標準の下線になる可能性がある。

### 採用した表示

未確定文字列を、細い一重の下線と炭火色の下線色を指定した`NSAttributedString`として渡す（`MarkedTextStyle.swift`）。背景色や文字色は指定しない。独自の重ね合わせウィンドウによる下線描画は行わない。

独自ウィンドウで下線を描く方式は、複数行、スクロール、縦書き、ブラウザ、文字サイズの違いへの対応が複雑になるため、初期実装には適さない。

### 実機での確認（Issue #22、2026-09-27、macOS 27）

| 入力先 | 装飾なしの文字列 | 細い下線を指定 |
|---|---|---|
| Chrome（Xの投稿画面） | 半透明の背景が重なり、範囲選択のように見える | 背景が消え、細い線だけになる。線は指定色ではなく白（暗い画面の文字色と思われる） |
| テキストエディット | 青い細線 | 青い細線（指定色は使われない） |
| メモ | 黄色の細線 | 黄色の細線（指定色は使われない） |
| ターミナル | 標準の下線 | 標準の下線（見た目は変わらないと報告） |

- 指定した色を反映したアプリはなかった。テキストエディットとメモは、それぞれのアクセントカラーで描く。
- メモでは点線の指定も実線になった。線の種類（点線・破線）は使わない。
- 同じプロセス内の`NSTextView`へ直接渡すと指定色の下線が描かれたので、色は入力先アプリとの間で使われなくなっていると考えられるが、どこで落ちるかは確かめていない。
- 下線を指定する主な効果は、Chromeで未確定文字列が選択範囲のように見えなくなること。

## 7. 変換処理

`Control + J`が押された後の処理案は次のとおりである。

最初に、直前に確定した変換を同じカーソル位置で再選択できるか判定する。対象文字列・範囲・入力先に変更がなく、安全に置換できる場合は候補ウィンドウを開き、次の再変換操作で第二候補以降を追加要求する。初回要求は第一候補1件だけとし、追加候補の先行取得はしない。以下は新しい追跡文字列を変換する場合の流れである。取得済み候補をさらに再表示する場合の再要求条件は未確定とする。

```text
Control + J
    │
    ├─ 現在の追跡文字列をスナップショットとして保存
    ├─ 入力セッションと更新番号を記録
    ├─ 追跡文字列の長さを検証
    │    └─ 1,000文字超ならエラーを表示し、原文を維持して終了（送信しない）
    ├─ 文脈利用がONの場合のみ、同じ入力領域の前後の文章を取得
    ├─ BYOKの設定と送信への同意を確認
    ├─ 設定済みのOpenAI互換APIを呼び出す
    │
    ├─ 応答時に入力状態が変わっていないか検証
    │
    └─ 問題がなければ原文を日本語へ置換して即確定（初回の候補選択は不要）
         └─ 待ち行列の入力を順番に処理（次の通信が始まれば再び待機）
```

通信はSwiftの非同期処理を使用し、入力メソッドのメインスレッドを停止させない。自己配布版では対応するmacOS 26以降でBYOKを必須とし、PCCの可否判定や自動切替は行わない。

追跡文字列は最大1,000文字とし、文脈の取得や変換バックエンドの呼び出しより前に検証する。超過時は通信エラーとは区別した文字数超過エラーにし、原文を維持する。切り詰め、自動分割、自動再試行によってこの制限を回避しない。確認項目は999文字・1,000文字・1,001文字の境界、空白・句読点・改行を含む入力、超過時にBYOKを呼び出さないこと、原文が維持されることである。周辺文脈の上限はこの1,000文字とは別であり、引き続き要検討とする。

PCCは[Appleの現行案内](https://developer.apple.com/private-cloud-compute/)ではApp Store配布アプリ向けの本番利用として説明される。自己配布版の変換経路へは含めず、将来Appleの提供条件が変わった場合に改めて検討する。

応答を適用する前に、少なくとも次の状態を検証する。

- 入力先アプリが同じである
- 入力セッションが同じである
- カーソル位置が変わっていない
- 追跡文字列が変わっていない
- IMEが引き続き有効である
- リクエストがキャンセルされていない

状態が変化していた場合、遅れて届いた変換結果を破棄する。これにより、別の入力欄や異なるカーソル位置へ結果が挿入される事故を防ぐ。

### 応答待ちと入力待ち行列

通信自体は非同期のまま、入力セッションごとに順序付きの待ち行列を持つ。文字とEnter・Backspace・`Control + J`を蓄積し、成功時は置換を完了してから入力順に処理する。次の`Control + J`によって通信が始まった場合は排出を中断し、残りと新たな入力を同じ順序で保持する。例えば`ohayou`を変換中に`gozaimasu`とEnterを入力した場合、「おはよう」の後ろに`gozaimasu`を反映した後でEnterを処理する。

待機中のEnterはまだ入力先へ渡していないため、そのキーだけを理由に応答を破棄しない。一方、マウス操作などによる実際の入力先・選択範囲の変更は別に検出し、古い結果や待機入力を別の欄へ適用しない。入力先変更時は変換をキャンセルし、待機中の文字をメモリ上に一時保留してメニューバーから確認・明示的なコピーで救済する。Enter・Backspace・`Control + J`は救済時に自動実行しない。救済用文字の保持期間・破棄操作と待ち行列の容量は未確定とする。

タイムアウト時間は60秒とし、初回変換と追加候補取得に適用する。

通信失敗またはタイムアウトで要求を終了した場合は、原文を変更せずに待機を解除し、元の入力先と対象が安全であることを確認して待ち行列を入力順に処理する。追加候補の取得失敗では、原文へ戻すのではなく現在確定済みの変換結果を維持する。終了済み要求の識別子を無効化し、遅れた応答による置換を防ぐ。待機中の文字は維持した文字列の後ろへ追加し、BackspaceやEnterも処理順に実行する。途中の`Control + J`が次の通信を開始した場合は、残りの入力を再び待機させる。失敗を理由とした自動再試行はこの処理に含めない。

失敗後の検証例は、原文`ohayou`に対して待機入力`gozaimasu`が`ohayougozaimasu`になること、Backspace・Enterを含む順序が維持されること、次の`Control + J`で待機が再開されること、遅延応答で入力が上書きされないこと、入力先変更時に誤って排出されないことである。

Enterを遅延して入力先アプリ本来の操作として実行する方法は、単なる改行文字の挿入と同一ではない。キーの遅延処理方式とアプリごとの互換性は試作で確認し、疑似キー送信や追加権限を必要とする方式を合意なく採用しない。文字と制御キーの順序維持、二重実行防止、連続する変換要求、入力先変更、追加候補待ちを検証対象とする。

### 7.1 前後の文章を文脈として利用する

この機能はデフォルトOFFである。利用者が設定画面でONにした場合のみ、変換開始時に`IMKTextInput`を通じて変換対象の前後の文章を要求する。取得できる範囲は入力先アプリの対応に依存する。位置や文字列を取得できない場合は文脈なしで変換し、片側しか取得できなければ取得できた側だけを使う。

原文と前後の文脈は別々のデータとして変換要求へ格納する。LLMには文脈を参考情報として提示し、その中の文章を命令として実行させず、変換結果には原文に対応する内容だけを返させる。文脈そのものは置換しない。

BYOKの変換要求で同じON／OFF設定を参照する。OFFの場合は文脈取得の処理を呼ばず、要求にも文脈を含めない。送信直前にも設定を確認し、OFFへ変更されていれば保持中の文脈を破棄する。既に送信した要求から情報を取り消すことはできない。文脈はログや設定ファイルへ保存せず、変換終了またはキャンセル時にも破棄する。

原文、周辺文脈、辞書、変換指示、追加候補要求時の現在の結果などを含む送信テキスト全体は1要求あたり1,000文字以内とし、要求を組み立てた後、BYOKへの送信直前に検証する。超過時は送信せずエラーにする。文脈の前後への配分と通信メタデータなどの計数規則は別途決定する。設定未保存時のOFF、ON時の前後取得、取得不能・片側のみ取得、OFFへの変更後の送信防止も実装時の確認対象とする。

## 8. 候補ウィンドウ

候補要求は「第一候補のみ」と「第二候補以降の追加取得」に分ける。iOS版の`ConversionCandidateMode`と追加候補取得処理を設計の参考にし、実装は共有しない。追加要求には保持している元の原文と現在の変換結果を渡す。追加取得は第一候補とは別に10件を要求し、有効な候補が少なくても件数合わせの自動再要求は行わない。

追加通信中や失敗時も、入力先の確定済み文字列を維持する。応答から候補を表示しただけでは自動置換せず、別候補を選んだときに対象を検証して置換する。送信直前の同意、入力長、BYOKの設定も初回と同じように検証する。周辺文脈は保持済みデータを再利用せず、その時点で設定がONの場合に限り、現在の変換結果の範囲を除いた前後から再取得する。

初回変換は応答取得後に即確定し、その直後にカーソルを移動せず`Control + J`を押すと候補ウィンドウを開く仕様とする。選択した別候補は直前の変換結果だけを置き換える。確定後の対象を再び編集するため、直前の原文・確定結果・範囲・入力セッション・候補を通常の追跡バッファとは分けてメモリ上で管理する。対象が変わった場合や位置を検証できない場合は適用せず、保持情報を破棄する。周辺文脈はこの保持情報に含めない。

Undoは入力先アプリの標準編集履歴へ委ね、Sumibi独自のキー割当や履歴によるUndoを実装しない。初回変換が原文の選択範囲へのペーストによる置換と同様に1回で取り消せること、候補切替が切替前の結果へ戻せることを検証する。クリップボード操作やキーイベントの疑似送信を採用するという意味ではない。IMEからの置換が入力先でどのようにUndoへ記録されるかは未検証であり、標準Undoを持つ全アプリで同じ結果になるとはまだ保証しない。

InputMethodKitには`IMKCandidates`という標準候補ウィンドウがある。候補の表示、選択、選択結果の通知を処理できる。

候補UIには次の選択肢がある。

### 8.1 IMKCandidatesを使用する

- macOSの他の入力メソッドに近い操作感になる
- キーボード操作や入力位置への追従を実装しやすい
- 独自デザインの自由度は低い

### 8.2 AppKitで独自ウィンドウを作る

- iOS版Sumibiに近い候補表示を実現できる
- 追加候補ボタンや独自の状態表示を配置できる
- 入力位置、画面端、複数ディスプレイ、縦書きなどへの対応が必要になる

初期実装では`IMKCandidates`を使用し、必要性が明確になった段階で独自候補ウィンドウを検討する方法を推奨する。この選択も製品仕様としては未確定である。

## 9. 設定画面

エラー表示はメニューバーのSumibiアイコンに印を付け、クリック時に詳細を表示する方式とする。入力位置付近や自動ポップアップでエラーを表示せず、通知バナー・音・モーダルダイアログで入力を中断しない。設定画面を開く入口と共存させ、原因と対処方法だけを示し、APIキー・原文・周辺文脈は表示しない。エラー確認を待ち行列の回復条件にしない。印の解除や複数エラーの扱いは別途設計する。

設定画面はSwiftUIで実装し、macOS標準のウィンドウとして表示できる。

設定項目と画面構成は、iOS版の`SumibiApp/SumibiApp.swift`にあるセクション分け、名称、並び順と詳細編集への導線を参照する。「Sumibiについて」「API設定」「入力設定」「文体プリセット」「ユーザー辞書」「変換テスト」「利用状況」「IMEの有効化手順」「プライバシー」を基本構成とし、macOSのウィンドウで使いやすいサイズに調整する。画面コードや設定保存コードをiOS版と共有することはない。

BYOKの設定とデフォルトOFFの文脈利用設定をmacOS版の仕様に合わせて追加する。PCCの状態や切替同意は自己配布版では表示しない。iOS用のフルアクセス案内はIMEの有効化手順に置き換え、触覚フィードバックなどの採用は未確定とする。変換テストにも入力長制限と送信同意を適用し、他アプリの文脈を取得しない。

設定画面で扱う項目（採用範囲は`SPEC.md`に従う）：

- BYOK用のAPIエンドポイント
- BYOK用のモデル名とAPIキー
- 前後の文章を文脈として利用する設定（デフォルトOFF）と、ON時に前後の文章も送信される旨の説明
- ユーザー辞書
- 変換指示プリセット
- プライバシー説明とデータ送信への同意
- 接続テスト
- モデル別の変換回数、取得可能なトークン数、算出可能な概算料金と集計リセット（不明な値は0としない）

設定画面への入口は、macOSのメニューバーに常時表示するSumibi専用アイコンとする。アイコンをクリックして表示するメニューの「Sumibi設定…」から、設定ウィンドウを開く。macOS標準の入力ソース切替メニューとは別に提供し、Sumibi IMEが選択されていない間も利用できるようにする。

このため、メニューバーの表示と設定画面の起動は、IMEの入力セッションの有効・無効に依存しない構成にする。構成は下の「実装済みの部分（メニューバー常駐）」を参照する。

アイコン素材はiOS版の`SumibiApp/Assets.xcassets/AppIcon.appiconset/AppIcon.png`をベースにする。形状・モチーフを保ち、少し濃い色に調整したmacOS版の素材をSumibi-mac側で独立して管理する。これは画像素材の流用であり、コードや共通パッケージの共有ではない。iOS版の元画像は変更しない。具体的な色味は両版の比較プレビューで決め、メニューバー用の小さい表示でも明暗の背景に対して見やすいことを確認する。

保存先の基本方針：

- BYOK用のAPIキー: macOS Keychain
- APIエンドポイント、モデル名、その他の一般設定: UserDefaults
- 入力内容、変換対象、周辺文脈の本文: 永続保存しない
- 利用状況の集計値: 入力本文を含めず端末内に保存する

### 実装済みの部分（変換処理）

BYOKでの実変換は実装済みである。

- `Sources/SumibiPrototypeCore/Conversion.swift`: 要求の型、1,000文字の上限、プロンプト組み立て、候補の取り出し。OSに依存せず自動テストの対象。

### 実装済みの部分（選択範囲の変換）

入力先で選択されている文字列を、そのまま変換対象にできる。未確定文字列がなく、追加候補にもならない`Control + J`を押したときに働く。

手順は次のとおりで、未確定文字列からの変換と同じ経路に載る。

1. `selectedRange()`で選択範囲を、`attributedSubstring(from:)`でその文字列を読む。どちらかが得られなければ何も書き換えず、理由をIMEメニューへ記録する。
2. 選択範囲を**同じ文字列で置き換える**。表示は変わらないが、この書き込みが新しい入力セッションを作らせ、応答を届けられるようにする（セッションの挙動は前述）。置換位置の記録（アンカー）もこのときに作る。
3. 応答が返ったら、記録した位置に記録した文字列がまだあることを確かめてから、変換結果で置き換える。

置換後のカーソルの形は入力先によって違う。メモは末尾のカーソルになり、Google Chromeは選択範囲が残る。どちらも「記録した位置に記録した文字列がまだある」ことに変わりはないため、照合ではカーソルの形を問わない。当初はカーソルが末尾にあることを条件にしていたため、Chromeでは変換が成功しても置換されなかった。

置換後のアンカーも、入力先が報告するカーソル位置ではなく、書き込んだ範囲と書き込んだ文字数から計算する。Chromeは書き込み直後に古いカーソル位置を返すことがあり、それを信じると次の置換位置がずれる。実際、Chromeでは初回変換のあとの追加候補が、位置の不一致で弾かれていた。

確定後に入力先が文字列を自動整形する場合（Issue #13）: 照合は記録した文字列との完全一致のままとし、大文字小文字や整形の差は許容しない。メッセージ（iMessage）は変換せずに送った`arigatou`を`Arigatou`に変えるが（Issue #4）、2026-09-27にmacOS 27で確かめたところ、Sumibiが確定した時点では整形されなかった。`arigatou`→「ありがとう」、`iphonewokau`→「iPhoneを買う」（英字始まり）のどちらも、初回変換・候補の出し直し・候補の選択ができ、照合は4回とも一致した。この環境では「文頭を自動的に大文字にする」と「スペース2回でピリオドを入力」がオンだった。整形は送信時か単語の区切りの入力時に起きるものと考えられるが、どちらかは確かめていない。

確認した入力先（2026-09-22）:

| 入力先 | 選択の読み取り | 置換 |
| --- | --- | --- |
| メモ（Notes） | できる | できる |
| TextEdit | できる | できる |
| Google Chrome | できる | できる（選択範囲が残る） |

### 実装済みの部分（ターミナル.app）

ターミナル.appでは初回変換ができる。候補の出し直しは、右Commandのタップか「かな」キーで行う（Issue #24・#26、2026-09-27、macOS 27で確認）。

- 書き込みの反映が遅れる: 原文を確定した直後、ターミナルが返すカーソル位置と文書の長さは書き込み前のままで、0.3秒後には原文の長さだけ進んでいた。確定直後の位置をアンカーにすると、応答時の照合で原文の長さだけずれて失敗し、変換結果が書き込まれなかった。
- 対処: 初回変換の応答時、カーソルが記録した位置より原文の長さだけ後ろにあり、記録した位置から原文がそのまま読めれば、書き込みが反映されたものとしてアンカーを改める（`reanchorIfCaretLagged`）。どちらかが合わなければ、これまでどおり置換を取りやめる。メモ・Chromeでは確定直後の位置が正しいので、この条件に当たらない。
- 置換: 範囲を指定した`insertText`は、ターミナルでもそのまま効いた（文書の長さが原文10文字ぶん減り、結果5文字ぶん増えた）。
- 候補の出し直しができない: 未確定文字列がないとき、ターミナルは`Control + J`をIMEへ回さず、シェルへ直接送る。変換後にもう一度`Control + J`を押すと、zshでは行が実行される。ログにもIMEがキーを受け取った記録はない。IMEからは防げないため、ターミナルでも届く変換キーを追加した（次節）。
- 未確定文字列の下線は、指定の有無にかかわらずターミナルが自分の表示で描く（6章）。

### 実装済みの部分（追加の変換キー）

`Control + J`のほかに、右Commandのタップと「かな」キーでも変換する（Issue #26）。ターミナルが未確定文字列のないときに`Control + J`をIMEへ回さないため、ターミナルでも届くキーとして選んだ。

ターミナルで未確定文字列がないときにIMEへ届くかを確かめた結果（2026-09-27）:

| キー | 届いたか |
| --- | --- |
| `Control + J` | 届かない（シェルへ直接送られる） |
| `Option + J`、`Option + Space` | 届かない（「Optionキーをメタキーとして使用」がオンのため） |
| `Shift + Space` | 届く（英文の入力中に誤って押しやすいため採らなかった） |
| 右Commandの押し下げ | 届く。離したことの通知は、ターミナルでは届かず、メモでも2回に1回だった |

- 右Commandのタップ: `recognizedEvents`に`flagsChanged`を加え、右Command（キーコード54）の押し下げを受け取る。離したことの通知は当てにならないため、押し下げを受け取ったら0.02秒ごとに`CGEventSource.flagsState`でCommandが離されたかを確かめる。0.4秒以内に離され、その間に`CGEventSource.counterForEventType`で数えたキー・マウスボタンの押し下げが増えておらず、押し下げ時にCommand以外の修飾キーがなければタップとみなす（判定は`CommandTap.swift`）。アクセシビリティの許可は要らなかった。タップはキーコードなしの`Control + J`として、キー処理の共通部分（`process`）へ渡す。
- 「かな」キー（キーコード104）: `Control + J`と同じ変換の操作として解釈する。利用者の環境ではKanaryが右Commandのタップを「かな」キーに変えて送っていた。このときSumibi自身のタップ判定は、押している間に「かな」キーが押されたとみなして働かないので、二重に変換しない。「かな」キーは、変換するものがなくても入力先へ渡さない。以前は入力先へ渡しており、ターミナルで行が意図しない内容（`exit`）に変わったが、原因は特定していない。
- 確認: ターミナル.appで、右Commandのタップによる初回変換・候補の出し直し・候補の選択ができた。Kanaryありでは「かな」キー経由、Kanaryを終了するとSumibi自身のタップ判定で動いた。メモでは`Control + J`と右Commandのタップの両方で変換できた。

### 実装済みの部分（ターミナル上のClaude Code）

ターミナル.appで動くClaude Codeの入力欄でも、初回変換・候補の出し直し・候補の選択ができる（Issue #28、2026-09-28、macOS 27で確認）。

ずれの規則:

- 描き直しで位置がずれる: Claude Codeは入力欄を自分で描き直すため、ターミナルが返す文字の位置番号が、書き込んだ時点と変わる。記録した位置には入力欄の罫線`───`などが返り、書き込んだ文字列はカーソルの直前へ移っていた。ずれは原文の確定後にも、変換結果での置換後にも起きる（例: 置換後の記録6061に対し、次のキーでのカーソル6209）。
- 折り返しで改行と字下げが挟まる: 長い入力は単語の区切りで折り返され、区切りの空白が「改行と2文字の字下げ」として返る。
- 変換結果のあとに文字を打つと直前の変換は取り消されるので、変換結果が残っていれば、書き込んだ文字列はいつもカーソルの直前にある。

対処: 記録した位置で文字列が一致しないとき、カーソルの直前に記録した文字列（折り返しを含む）が読めれば、そこを置換位置として記録し直す（`reanchorAtCaret`、`validatesAnchor`、照合は`WrappedText`）。応答時の照合と、候補の出し直し・候補の選択の前の照合で働く。どのアプリでも働くが、完全一致が通らなかったときだけで、記録した文字列と違う文字列は置換しない。候補の出し直しの後にClaude Codeのヒストリーで入力欄が変わった場合は、照合が通らず置換を取りやめた。

候補の選択: ターミナルは未確定文字列がないとき、矢印キーをIMEへ回さない。候補の窓を出したまま↓を押すと、Claude Codeのヒストリーの呼び出しになった。数字キーと変換キーは届くので、候補の窓では次の操作も受け付ける。

- 数字キー1〜9: 窓に付けた番号の候補に決めて、窓を閉じる。
- 変換キー（右Commandのタップ、「かな」キー、`Control + J`）: 次の候補へ移り、窓を開いたまま入力欄の文字列をその候補に書き換える。ターミナルでは決定のキーも届かないため、移った時点で書き換える。最後の候補の次は先頭へ戻る。
- メモ・Chromeでの↓↑とEnter、Escの動きは変えていない。

確認: ターミナル.appのClaude Codeで、短い原文の初回変換、右Commandのタップでの候補の出し直し、変換キーでの候補送り、数字キーでの決定ができた。今回の試験では、候補の出し直しの前に位置はずれず、カーソルの直前への記録し直しは働いていない。Codex CLIなど他のTUIでは確かめていない。

### 実装済みの部分（対象外のアプリ）

Emacs.appの中では変換を行わず、キーをすべてEmacsへそのまま渡す（仕様は[仕様書の3.5](SPEC.md#35-対象外のアプリ)）。

- 判定: 入力先の`bundleIdentifier()`を、`Sources/SumibiPrototypeCore/ExcludedApplications.swift`の一覧と大文字小文字を区別せずに比べる。一覧は`org.gnu.Emacs`と`org.gnu.Aquamacs`。GNU Emacs本体・Emacs Mac PortのInfo.plistは`org.gnu.Emacs`、Aquamacsは`org.gnu.Aquamacs`であることを各配布元のソースで確かめた。emacs-plusはGNU Emacsのソースをそのままビルドするため、識別子も同じである。識別子が得られない入力先は対象外にしない。
- `handle(_:client:)`: 対象外のアプリでは、キーを解釈する前に`false`を返す。`Control + J`はEmacsの`C-j`として動く。
- 他のアプリの入力を終える: 対象外のアプリで`activateServer`または`handle`が呼ばれたとき、他のアプリで追跡中・応答待ち中・候補窓の表示中なら、別アプリへの切り替えと同じ`cancelForTargetChange()`で終える。変換要求は取り消し、未確定だった文字は保留文字としてIMEメニューから救済できる。
- 書き込み先から外す: 状態はプロセス全体で1つ（`PrototypeRuntime`）のため、応答の書き込み先を探す`liveInput()`と`completeIfReady`から、対象外のアプリの入力先を除く。対象外のアプリのセッションは`runtime.latest`にしない。
- `deactivateServer`・`commitComposition`: 対象外のアプリでは何もしない。何も書いていないので確定するものがなく、ここで状態を消すと移った先の入力を壊しうる。
- IMEメニュー: 入力先が対象外のアプリのとき、選択できない項目「Emacs.appではEmacs版のSumibiを使ってください」を出す。

### 実装済みの部分（API設定）

API設定（APIのURL、モデル名、APIキー）は実装済みである。

- 画面: `Sources/SumibiPrototypeIME/Settings/APISettingsView.swift`。SwiftUIの`Form`をNSHostingViewでウィンドウへ載せる。

- APIのURLは`https`を必須とし、`http`は`localhost`・`127.0.0.1`・`::1`に限って許す。手元で動かすLLMサーバーを試せるようにするためである。

### 実装済みの部分（メニューバー常駐）

メニューバーのSumibiアイコンと、そこから設定を開くメニューは実装済みである。

- コード: `Sources/SumibiPrototypeIME/MenuBar/MenuBarController.swift`。`NSStatusItem`を起動時に1つ作る。
- **IMEと同じプロセスに置く。** 入力ソースとしてSumibiが選ばれていなくても、プロセスが動いている間はアイコンが出続ける。別プロセスのヘルパーにしなかったのは、設定（`UserDefaults`）とKeychainを共有するためにApp Groupやアクセスグループが要り、署名と配布の手間が増えるためである。設定画面で保存した値を、変換がそのまま読めるという利点もある。
- **ログイン時の起動。** ログイン直後はSumibiを一度も選ばなければIMEのプロセスが起動せず、アイコンも出ない。そこでIMEのアプリ自身を`SMAppService.mainApp`でログイン項目へ登録する。IMEのプロセスが先に動いていても、Sumibiを選べばIMKはそのプロセスへ接続する。`open`で起動したプロセスのまま入力コントローラーが作られ`activateServer`が呼ばれること、2つ目のプロセスが起動しないことを確認した（2026-09-23）。
- 登録は初回起動時に自動で行う。`SMAppService.mainApp.status`は、一度も登録していない状態でも`.notRegistered`ではなく`.notFound`を返した（macOS 27、`~/Library/Input Methods`に置いた場合）。このため、`.enabled`・`.requiresApproval`以外なら登録を試す。
- メニューの「ログイン時に起動」で登録を取り消せる。取り消したことは`UserDefaults`のキー`MenuBarLoginItemOptOut`に記録し、次に起動したときも自動では登録し直さない。システム設定の「ログイン項目」で切られた場合（`.requiresApproval`）は、アプリからは戻せないため、メニューからその設定画面を開く。
- メニュー: 「Sumibi設定…」「ログイン時に起動」。エラーの印と詳細の表示は、失敗の知らせ方を決める別Issue（#12）で追加する。
- アイコン: iOS版の`AppIcon.png`（橙地に黒の線画）から線画だけを取り出したテンプレート画像。`Prototype/MenuBarIcon.swift`で作り、生成物の`Prototype/Resources/MenuBarIcon.png`・`MenuBarIcon@2x.png`（18pt）をリポジトリで管理する。iOS版の元画像は変更しない。テンプレート画像なので、システムが他のメニューバー項目と同じ色（明るい背景では黒、暗い背景では白）で描く。

確認したこと（2026-09-23、macOS 27。IMKの接続を除き、入力ソースは`ABC`のまま）:

| 項目 | 結果 |
| --- | --- |
| Sumibiを選ばずにプロセスを起動したときのアイコン | 表示された |
| メニューの表示 | 「Sumibi設定…」と、チェック付きの「ログイン時に起動」が出た |
| 「Sumibi設定…」 | 設定ウィンドウが開いた |
| `open`で起動したプロセスへのIMKの接続 | 同じプロセスで`activateServer`まで届いた。メモで`ohayou` → `Control + J`の変換も成功した |
| ログイン項目への登録 | `status`が`.enabled`になった |
| 暗いメニューバーでの見え方 | 白で描かれ、他のアイコンと並べて判別できた |
| 明るいメニューバーでの見え方 | 黒で描かれ、他のアイコンと並べて判別できた。試したMacではメニューバーの色が外観ではなく壁紙で決まるため、壁紙を明るい単色（Silver）に一時的に変えて確かめた |
| ログイン時の自動起動 | 再ログイン後、Sumibiを選ばないうちにアイコンが出た。`loginwindow`がログイン項目として起動しており（ログの`LoginItemsLauncher`・`performAutolaunch`）、ウインドウの復元による起動ではない。プロセスは1つだけだった |

## 10. インストールと有効化

InputMethodKitを使用するアプリは、通常のmacOSアプリとは起動方法が異なる。

自己配布版の概念的な導入手順は次のとおりである。

1. IMEと、設定・メニューバーを担当するアプリをビルドし、Developer IDで署名する。
2. 署名・公証済みのインストーラーで、それぞれを適切な場所へ配置する。
3. 必要に応じてログアウトまたは入力メソッド関連プロセスを再起動する。
4. システム設定の「キーボード」からSumibiを入力ソースへ追加する。
5. 入力ソースメニューからSumibiを選択する。

Mac App Storeでの配布は見送る。配布物はGitHub Releasesの署名・公証済みインストーラーとし、GitHub Pagesのダウンロードページから案内する。導入場所、ログイン項目の登録、更新・アンインストール時の扱いは、[自己配布の設計と検証項目](DIRECT_DISTRIBUTION.md)に従って具体化する。上記の手順はまだ実機で検証していない。Mac App Store方針を変更した背景は[調査記録](MAC_APP_STORE_FEASIBILITY.md)を参照する。

### 10.1 製品版の識別子と表示名（Issue #11）

| 項目 | 試作版 | 製品版 |
| --- | --- | --- |
| バンドル識別子 | `dev.kiyoka.inputmethod.SumibiPrototypeProbe1` | `org.sumibi.inputmethod.Sumibi` |
| 入力ソースID（日本語モード） | `…SumibiPrototypeProbe1.Japanese` | `org.sumibi.inputmethod.Sumibi.Japanese` |
| `InputMethodConnectionName` | `…SumibiPrototypeProbe1_Connection` | `org.sumibi.inputmethod.Sumibi_Connection` |
| 表示名（日・英） | Sumibi 試作版 / Sumibi Prototype | Sumibi / Sumibi |
| アプリ | `SumibiPrototypeIME.app` | `Sumibi.app`（実行ファイル`Sumibi`） |
| 診断ログのsubsystem・設定の保存先 | 試作版の識別子 | 製品版の識別子 |

- 識別子は頭の`org.sumibi.`をiOS版（`org.sumibi.Sumibi-iOS`）とそろえ、#4 で登録が通った`.inputmethod.`を含める。iOS版と同じ識別子にしないのは、Apple シリコンのMacへiOS版が入ったときに同じ識別子のアプリが2つになるためである。
- 表示名はiOS版のアプリ名・キーボード名と同じ「Sumibi」とする。
- アプリアイコンは、iOS版の線画を地の色`#CC6508`のmacOSの角丸の正方形に描いたもの（`Prototype/AppIcon.swift`、`Prototype/Resources/AppIcon.png`）。入力メニューのアイコンは、メニューバーのアイコンと同じ線画だけの型抜き画像にし、`TISIconIsTemplate`を指定する。macOSは入力メニューのアイコンを型抜きとして描くため、地の塗られた画像は豆腐のような四角になった。
- 試作版で保存した送信先・モデル・同意は、製品版の初回起動時に一度だけ写す（`SettingsStore.importPrototypeSettingsIfNeeded`）。製品版に送信先の設定がないときだけ写し、試作版の設定は消さない。APIキーはKeychain（サービス名`org.sumibi.Sumibi-mac.api-key`）にあり、識別子に依存しない。

試作版からの切り替え手順（2026-09-28、macOS 27で確認）:

1. 入力ソースを`ABC`に戻す。
2. `pkill -x SumibiPrototypeIME`で試作版を終了し、`~/Library/Input Methods/SumibiPrototypeIME.app`をゴミ箱へ移す。入力ソースの一覧から試作版はすぐに消えた。
3. `Sumibi.app`を`~/Library/Input Methods/`へ置き、起動する。同じログインのまま、本体と日本語モードが表示名「Sumibi」で入力ソースの一覧に現れた。本体はシステム設定で追加するまで無効（`apiEnabled=false`）。
4. システム設定の「キーボード」→「入力ソース」で「Sumibi」を追加する。項目名・副題とも「Sumibi」で現れ、追加すると本体も有効になった。変換もでき、設定は引き継がれていた。
5. 入力メニューのアイコンは、このログインの間は最初に読み込んだ画像のまま変わらなかった。入力ソースを外して追加し直しても変わらず、ログアウト・ログインで新しい画像になった。

記憶される表示名とアイコン:

- #4 では、`InfoPlist.strings`を直してもそのログインの間は古い表示名が残った。今回は識別子ごと新しくしたため、表示名は初めから正しく出た。
- 入力メニューのアイコンは、識別子ごとに最初に読み込んだ画像がログインの間は記憶される。同じ識別子のまま画像を差し替えると、反映には再ログインが要る。製品版のアイコンは確定したので、利用者に再ログインを求めるのは、配布後にアイコンを変える場合に限られる。
- 再ログイン後、Sumibiはログイン直後に起動し、メニューバーのアイコンが出た。ログイン項目として起動したことを示す記録（`LoginItemsLauncher`）は、今回のログでは確かめていない。

## 11. 初期実装の推奨順序

1. InputMethodKitで最小の入力メソッドを起動する
2. 通常文字の入力と未確定文字列の表示を実装する
3. Backspace、カーソル移動、IME切り替えを安全に処理する
4. `Control + J`で固定の文字列へ置換する試作を作る
5. Sumibi-iOSを参照してOpenAI互換APIクライアントを追加する
6. 変換中の状態検証とキャンセルを追加する
7. Keychainと設定画面を追加する
8. 候補表示、Undo、ユーザー辞書を順番に追加する
9. 複数アプリで互換性を検証する
10. Developer ID署名・公証済みインストーラーを作成し、導入・更新・削除を検証する
11. GitHub Releasesにインストーラーを公開し、GitHub Pagesのダウンロードページを整備する

最初からすべての機能を実装せず、入力メソッドとしての安全な文字追跡と置換を先に検証する。
